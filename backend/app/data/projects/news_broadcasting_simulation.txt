--- EXECUTIVE SUMMARY ---
A multithreaded news broadcasting simulation in C
demonstrating the classic Producer-Consumer concurrency pattern. Multiple producer threads
generate categorized news stories (Sports, Weather, News) which flow through a dispatcher,
co-editors, and finally to a screen manager—all using carefully synchronized bounded and
unbounded buffers.

--- ARCHITECTURAL STRATEGY / TECHNICAL APPROACH ---

1. Multi-Stage Pipeline Architecture:
   - **Context:** Needed to simulate real-world news production where stories pass through
     multiple processing stages before display.
   - **Solution:** Designed a 4-stage pipeline: Producers → Dispatcher → Co-Editors →
     Screen Manager, each running in separate threads.
   - **Reasoning:** Decoupled design allows independent scaling and simulates real workflows
     where content creation, routing, editing, and display happen concurrently.

2. Custom Bounded Buffer Implementation (Thread-Safe Queue):
   - **Context:** Critical sections where multiple threads access shared queues created
     race conditions and potential buffer overflows.
   - **Solution:** Built bounded buffer using circular array with three semaphores: a mutex
     for mutual exclusion, and "full"/"empty" counting semaphores for coordination.
   - **Reasoning:** Classic OS solution prevents data corruption AND handles full/empty
     edge cases elegantly without busy-waiting.

3. Dual Buffer Strategy (Bounded vs. Unbounded):
   - **Context:** Producer queues need backpressure to prevent memory exhaustion, but
     dispatcher output queues need flexibility.
   - **Solution:** Bounded buffers (fixed-size arrays) between Producers and Dispatcher;
     unbounded buffers (linked lists) between Dispatcher and Co-Editors.
   - **Reasoning:** Bounded buffers throttle fast producers; unbounded buffers prevent
     dispatcher bottlenecks since co-editors have predictable processing times.

4. Round-Robin Fair Scheduling:
   - **Context:** Dispatcher must read from multiple producer queues without starving
     any producer.
   - **Solution:** Dispatcher cycles through producer queues in round-robin order.
   - **Reasoning:** Ensures fairness regardless of production rate; simpler and more
     predictable than priority-based schemes.

--- KEY TECHNICAL CHALLENGES ---

**Race Condition Prevention:**
- Problem: Multiple producers writing to Dispatcher queue simultaneously risked corruption.
- Solution: All queue operations wrapped in strictly scoped mutex locks.

**Graceful Shutdown (Deadlock Prevention):**
- Problem: Consumers could block forever waiting for data that will never come.
- Solution: "DONE" sentinel message protocol—producers signal completion, Dispatcher
  tracks and propagates shutdown signal through entire pipeline cleanly.

--- TECH STACK BREAKDOWN ---

**Core:**
- **Language:** C (systems-level memory and thread control)
- **Threading:** POSIX Threads (pthreads)
- **Synchronization:** POSIX Semaphores (binary mutexes + counting semaphores)

**Build & Runtime:**
- **Build System:** Makefile with gcc and -pthread flag
- **Configuration:** External config file for dynamic producer/queue setup
- **Platform:** Linux/Unix (POSIX-compliant systems)

--- KEY FEATURES ---
- Multiple concurrent producers generating randomized news categories
- Thread-safe bounded buffer with configurable sizes per producer
- Unbounded queue implementation using linked list for dispatcher outputs
- Round-robin message dispatch with automatic type-based routing
- Simulated editing delay (100ms) to model real processing time
- Graceful shutdown with "DONE" sentinel propagation through all stages
- Dynamic configuration via external file (producer count, queue sizes)

--- ENGINEERING PHILOSOPHY DEMONSTRATED ---
1. **Low-Level Concurrency:** Deep understanding of mutexes and semaphores at the OS
   level, not just high-level async/await abstractions.
2. **Pipeline Architecture:** Separation of concerns across distinct processing stages.
3. **Robust System Design:** Graceful shutdowns, bounded resource usage, deadlock prevention.
4. **Debugging Complexity:** Managing non-deterministic multi-threaded execution.
